# Аполлонов и Шигапова — сайт (ashpartners.ru)

Статический одностраничник без сборки. Разметка — `site/index.html`,
**весь CSS — `site/site.css`, весь JS — `site/site.js`** (вынесены из
разметки, чтобы не читать файл на 2500 строк ради одной правки).
Подробная карта с номерами строк — в `docs/site-map.md`, **читай её
первой в новом чате и открывай файлы точечно по ней**, а не целиком:
это основная экономия токенов.

## Другие клиенты в этом репозитории

Кроме ashpartners.ru, в `site/diana/` ведётся прототип для другого клиента
(Perfect Ton by Diana Fedorova). Для новых клиентских проектов "под ключ"
(не мелкая правка, а сайт с нуля) — используй навык
`.claude/skills/wireframe-first/SKILL.md`: бриф → структура → чёрно-белый
каркас (структура+текст в одном, без цвета) → правки клиента → и только
потом дизайн одного экрана → остальные страницы. Каркас удобно публиковать
через Artifact, чтобы отправить клиенту одной ссылкой.

**Живой сайт:** `https://alina3500-2-arch.github.io/project-s-sashey/`
(GitHub Pages, деплоится автоматически при пуше в `main`, workflow
`.github/workflows/pages.yml`). Это теперь основной канал показа сайта.

## Прежде чем что-то менять

1. **Проверь git-расхождение.** Сайт правится из нескольких мест (этот
   инструмент и Codex — не только этот чат). Перед любым push:
   ```
   git fetch origin main
   git log --oneline -1 main
   git log --oneline -1 origin/main
   ```
   Если у origin/main есть коммиты, которых нет в локальном main —
   **не пушить и не мерджить молча**. Посмотреть `git show <коммит> --stat`,
   понять, что изменилось, показать пользователю и спросить. Никогда не
   force push. Если попросят принять чужую версию как основу —
   `git reset --hard origin/main`, но только с явным подтверждением
   (это стирает локальные коммиты, которых нет на GitHub).
2. **Открой `docs/site-map.md`** — там актуальный список блоков, что где
   лежит, какие ассеты реальные, какая структура у кейса Eco-Store.
3. Сервер для локальной проверки: `cd site && python3 -m http.server 8899`
   (лучше в фоне через `nohup ... & disown`, чтобы не блокировать сессию).
   Скриншоты — Playwright, `executable_path="/opt/pw-browsers/chromium-1194/chrome-linux/chrome"`.

## Стоп-правила (из опыта этого проекта)

- **Не выдумывать кейсы/цифры/отзывы.** Если данных нет — плейсхолдер с
  пометкой или прямой вопрос, никогда не фантазировать реальные цифры.
- **«Один в один макет»** — значит буквально: если что-то не удалось
  повторить пиксель в пиксель, сказать прямо, какой элемент и почему,
  а не подгонять на глаз и не молчать об отличиях.
- **Текст внутри блока кейса (05) теперь живой HTML**, не картинка —
  правки текста там дешёвые, обычное редактирование. Вставлять новый
  текст КАРТИНКОЙ (как было в самой первой версии кейса) — плохая идея,
  так делать больше не нужно.
- **Не «чинить» то, что согласовано.** Зелёный фон и вспышка на лестнице
  «4 шага» — часть согласованного рендера, а не баг: один раз это уже
  приняли за ошибку, подменили картинку и пришлось откатывать. Если
  элемент выглядит странно, но лежит в `main` давно — сперва
  `git log --oneline --all -- <файл>` и спросить, а не переделывать.
- Перед push — обязательно тестировать: Playwright на нескольких ширинах
  (360/390/560/900/1280/1440/1920), проверять `hscroll=false`, отсутствие
  наложений, отсутствие ошибок в консоли (`page.on("pageerror")`) и 404
  (`page.on("response")`).
- Если правка не должна менять вид — сверять **пиксель-дифом** (старая
  версия из `git archive HEAD` на соседнем порту + `PIL.ImageChops`),
  а не просмотром скриншотов глазами. Рецепт — в `docs/site-map.md`.

## Экономия токенов — обязательно к соблюдению

Самое дорогое в этом проекте — не код, а **картиночная сверка** (скриншоты,
кропы макетов, подбор шрифтов по пикселям, ручная отрисовка текста поверх
растра). Каждое такое изображение в контексте стоит как несколько страниц
текста. Экономия строится вокруг этого факта:

1. **Новый чат под новый блок работы.** Не продолжать один чат весь день —
   старые скриншоты и макеты остаются в контексте и утяжеляют каждый
   следующий шаг. Один блок правок (или одна сессия ~1-2 часа) — один чат.
2. **Собирать правки в один список**, не присылать по одной фразе за раз.
   Пять правок одним сообщением дешевле, чем пять сообщений по одной.
3. **Пиксель-в-пиксель — только когда реально нужно.** Подбор шрифта по
   картинке (перебор гарнитур/кеглей с чтением результата обратно) — самая
   дорогая операция в проекте. Почти всегда дешевле сделать вёрстку
   текстом (живым HTML), а не встраивать текст в изображение — так и
   редактировать потом легче. Именно поэтому кейс Eco-Store в итоге
   пересобран на живой вёрстке, а не на слайдах-картинках.
4. **Если правка касается уже готового визуала — просить финальный текст
   заранее**, а не переспрашивать по одному слову после того, как всё
   сверстано.
5. **Меньше скриншотов за проверку.** Один скриншот всей секции лучше пяти
   скриншотов отдельных фрагментов, если задача позволяет.
6. **Не читать одно и то же изображение повторно** без необходимости —
   если состояние не менялось, повторный Read не добавляет информации.

## Какую модель использовать

В `/model` можно переключать модель прямо в сессии. Правило:

| Задача | Модель |
|---|---|
| Точечная правка текста, цвета, отступа, замена ссылки/цифры (текст живой, не в картинке) | **claude-sonnet-5** |
| Мелкие CSS-фиксы, которые не требуют сверки с картинкой | **claude-sonnet-5** |
| Пересборка блока по макету «один в один», работа с изображениями/шрифтами/пиксельной сверкой | **claude-opus-5** |
| Массовая проверка адаптива на многих ширинах, отладка сложных наложений/анимаций | **claude-opus-5** |
| Если не уверены — начинайте с Sonnet, переключайтесь на Opus только если задача забуксовала | — |

Не держать Opus включённым «на всякий случай» для простых правок — это и есть
основной источник лишнего расхода при простых задачах.

## Деплой

Основной канал — **GitHub Pages**, срабатывает сам при пуше в `main`
(см. выше). Отдельно есть путь на реальный хостинг Majordomo через
`deploy/deploy.py` — см. `docs/deploy.md` и `docs/workflow.md`, это для
случая, если понадобится залить именно на `ashpartners.ru`, а не только
показать превью на GitHub Pages.
