# Инструкция по редактированию сайта ashpartners.ru

Для любого ИИ-агента (Codex, Claude Code и т.д.). Главный приоритет —
**экономия токенов**. Ниже сначала правила, потом карта файлов.

---

## 1. Первые три действия в новой сессии

```
git fetch origin main && git log --oneline -1 origin/main   # 1. чужие правки?
cat AGENTS.md                                               # 2. этот файл
```

3. Открывать файлы **точечно по номерам строк из карты ниже**
   (`Read(file, offset, limit)`), а не целиком. `site.css` — 1635 строк,
   читать её полностью ради одной правки нельзя.

Если у `origin/main` есть коммиты, которых нет у вас — **не пушить и не
мерджить молча**: показать `git show <коммит> --stat` пользователю и
спросить. Force push — никогда.

## 2. Откуда берётся расход и как его не создавать

Дорогой в этом проекте не код, а **картинки в контексте**: один скриншот
стоит как несколько страниц текста. Отсюда правила по убыванию важности:

1. **Один блок работы — один чат.** Главное правило. Старые скриншоты
   остаются в контексте и утяжеляют каждый следующий шаг: сессия
   деградирует — «чем дальше, тем хуже понимает и быстрее тратит».
   Закончили блок правок — новый чат.
2. **Проверять пиксель-дифом, а не глазами** (рецепт в §6). Проверка
   «ничего не поехало» стоит одну строчку вывода вместо десятка картинок.
   Смотреть скриншот только там, где диф показал отличия.
3. **Открывать файлы точечно** по карте, не грепать вслепую.
4. **Правки собирать списком.** Пять правок одним сообщением дешевле, чем
   пять сообщений по одной.
5. **Один скриншот всей секции** лучше пяти скриншотов фрагментов.
6. **Не перечитывать то же изображение**, если состояние не менялось.
7. **Текст верстать живым HTML, а не растром.** Текст, вшитый в картинку,
   превращает правку одного слова в пиксельный подбор шрифта — самая
   дорогая операция из возможных. Весь текст в кейсах уже живой HTML.

**Дальше дробить не нужно.** Разбивать `site.css` на файлы по блокам —
выигрыш уже отрицательный: появится путаница, что где, и лишние чтения.

бренда, по 4 тыс. символов. Вынести в файл нельзя (красится через
`var(--ash-cream)` и `.mk-arc` из CSS). Просто не грепать по ним.

## 5. Стоп-правила (все — из реальных ошибок в этом проекте)

- **Не выдумывать кейсы, цифры, отзывы.** Нет данных — плейсхолдер с
  пометкой или прямой вопрос. Никогда не фантазировать цифры.
- **Не «чинить» то, что согласовано.** Зелёное свечение и вспышка на
  лестнице «4 шага» когда-то приняли за баг, подменили картинку — пришлось
  откатывать; потом выяснилось, что нужен был как раз чистый рендер, и
  откатывать пришлось второй раз. Если элемент выглядит странно, но лежит
  в `main` давно — сперва `git log --oneline --all -- <файл>` и **спросить**.
- **«Один в один макет» — буквально.** Не удалось повторить пиксель в
  пиксель — сказать прямо, какой элемент и почему. Не подгонять на глаз
  и не молчать об отличиях.
- **Не трогать `is-loading` без понимания.** Пока класс висит на `<html>`,
  CSS прячет всё содержимое (`visibility:hidden`). Снимается в `site.js`
  с предохранителем 1,5 с. Раньше ждали `window.load` — один упавший
  запрос (шрифты Google, недоступные в России) держал сайт пустым экраном
  ~15 секунд. **Предохранитель не удалять.**
- **Внешние ресурсы не должны блокировать отрисовку.** Google Fonts
  подключён неблокирующе (`media="print"` + `onload`). Так и оставить.

## 6. Проверка перед push — обязательна

Локальный сервер: `cd site && python3 -m http.server 8899`
(в фоне: `nohup ... & disown`, иначе блокирует сессию).
Playwright: `executable_path="/opt/pw-browsers/chromium-1194/chrome-linux/chrome"`.

Минимум на ширинах 360/390/560/900/1280/1440/1920:
`hscroll=false`, нет ошибок консоли (`page.on("pageerror")`),
нет 404 (`page.on("response")`).

**Если правка не должна менять вид — пиксель-диф, а не просмотр глазами.**
Это и есть главная экономия:

1. `git archive HEAD site | tar -x -C /tmp/before`, поднять на 8898;
2. текущую версию — на 8899;
3. снять одни и те же секции в обоих, сравнить `PIL.ImageChops.difference`;
4. глазами смотреть только то, где `diffpx > 0`.

Так проверялись вынос CSS/JS и переформатирование слайдов: 20 состояний
вкладок кейсов на двух ширинах — 0 отличающихся пикселей, без единого
просмотра картинки.

## 7. Картинки

Все файлы в `site/assets/` используются, кроме `ash-mark.svg` (знак вшит
inline). 17 из 18 `<img>` помечены `loading="lazy"` — исключение только
лестница, она выше сгиба. **Новым картинкам ниже первого экрана тоже
ставить `loading="lazy" decoding="async"`.**

Найти неиспользуемые:

```
cd site && comm -13 \
  <(grep -oh 'assets/[A-Za-z0-9._-]*' index.html pc.html site.css | sed 's|assets/||' | sort -u) \
  <(ls assets | sort)
```

Новые картинки перед коммитом сжимать (JPEG q≈82).

## 8. Деплой и git

Живой сайт: `https://alina3500-2-arch.github.io/project-s-sashey/`
ПК-версия с телефона: `.../pc.html`

Деплоит `.github/workflows/pages.yml` при пуше в `main`, публикует папку
`site/` **как корень** — поэтому в URL нет `/site/`.

⚠️ **Локальная ветка `main` в некоторых сессиях — это вообще другой
проект** (нет общей истории с `origin/main`, `git merge` падает с
`unrelated histories`). Проверять `git log --oneline -1 main` перед
работой с ней. Надёжный способ — не трогать локальный `main`:

```
git merge-base --is-ancestor origin/main HEAD && \
git push origin <моя-ветка>:main
```

| Задача | Модель |

источник лишнего расхода на мелочах.
